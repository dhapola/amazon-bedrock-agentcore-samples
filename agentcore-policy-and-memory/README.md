# CustomerSupport

## Overview

`CustomerSupport` is an Amazon Bedrock AgentCore project generated by the AgentCore CLI. It has three parts:

- `app/agent/` — the Python runtime code (Strands Agents SDK inside a `BedrockAgentCoreApp`), deployed as a CodeZip on `PYTHON_3_14`.
- `agentcore/` — project config and infra. `agentcore/agentcore.json` is the source of truth for what gets deployed (runtimes, memories); `agentcore/cdk/` is a CDK app that turns that JSON into CloudFormation via `@aws/agentcore-cdk`.
- `tools/` — local client scripts against the deployed stack (not deployed): `chat.py` (interactive chat with the runtime, incl. refund approvals) and `memory_query.py` (read-only inspection of AgentCore Memory; docs in `tools/README_memory_query.md`).

There are no tests or linters configured yet.

## Commands

Run AgentCore CLI commands from the project root (they read `agentcore/`):

```bash
agentcore dev                                                   # local server on 0.0.0.0:8080 (loads agentcore/.env.local)
agentcore build                                                 # synth CloudFormation into agentcore/cdk/cdk.out
agentcore deploy                                                # synth + deploy stack for the selected target
agentcore status                                                # report resources declared in agentcore.json
agentcore invoke --runtime agent --payload '{"prompt":"Hello!"}'
AWS_ACCOUNT_ID=<id> agentcore/write-aws-targets.sh              # generate agentcore/aws-targets.json (needed before deploy)
```

Client tools (from the project root, using the agent venv; both need AWS credentials for the deploy account):

```bash
AWS_ACCOUNT_ID=<id> app/agent/.venv/bin/python tools/chat.py --actor-id cli-user   # /new = new session, /quit
app/agent/.venv/bin/python tools/memory_query.py list                             # what's in memory; also actors/sessions/events/records/search/record/dump
```

Global flags of `memory_query.py` (`--json`, `--memory-id`, `--region`) go before the subcommand.

Python env (uses `uv`; lockfile at `app/agent/uv.lock`): `cd app/agent && uv sync && source .venv/bin/activate`.

CDK directly (from `agentcore/cdk/`): `npm run build` (tsc → `dist/`), `npx cdk synth`, `npx cdk diff`. Normally the CLI runs this for you — prefer `agentcore build` to synth (plain `npx cdk synth` exited silently without producing `cdk.out` in this environment).

## Architecture

**Request flow** (`app/agent/main.py`): `@app.entrypoint invoke(payload, context)` → `parse_payload()` (`parse.py`) returns `(prompt_or_messages, actor_id)` → `_get_agent(session_id, actor_id)` builds a Strands `Agent` → events from `agent.stream_async()` are filtered and yielded as a stream.

- `session_id` comes from the `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` header (`context.session_id`), not the payload; falls back to `"default-session"`.
- Payload: `messages` (full history, takes precedence; trailing `toolUse` blocks are stripped by `_strip_trailing_tool_use()` — keep this) or `prompt` (string) or `interruptResponses` (resume after an approval pause, see below), plus optional `actorId` (default `"default"`).
- `_get_agent` is `lru_cache`d per `(session_id, actor_id)`, so agents (and their in-memory state) persist across invocations within a process. Uses `NullConversationManager` (no history trimming).
- Tools: plain `@tool` functions appended to the module-level `tools` list in `main.py`.
- Model: `model/load.py` returns a `BedrockModel` (IAM credentials). Change the model ID there.

**Memory** (`app/agent/memory/session.py`; inspect with `tools/memory_query.py`): only enabled when env var `MEMORY_AGENTMEMORY_ID` is set (injected at deploy for the `agentMemory` memory declared in `agentcore.json`); otherwise the agent runs with no session manager. Retrieval namespaces in `session.py` must line up with the strategy `namespaceTemplates` in `agentcore.json` — note the SUMMARIZATION strategy writes to `/summaries/{actorId}/{sessionId}` while `session.py` retrieves from `/summaries/{actor_id}`. When adding/renaming memory strategies, update both files. The Strands session manager stores each message as a JSON envelope inside the event's `conversational.content.text`, plus `blob` events for session/agent state.

**Gateway / refunds**: `agentCoreGateways[]` in `agentcore.json` declares the `refunds` gateway (`AWS_IAM` inbound auth, MCP) with a `lambdaFunctionArn` target pointing at the pre-existing `process_refund` Lambda (not managed by this project). Its tool schema lives in `agentcore/tools/process-refund.json` — `toolSchemaFile` paths resolve from the project root, not `agentcore/`. On deploy the runtime gets `bedrock-agentcore:InvokeGateway` and `AGENTCORE_GATEWAY_REFUNDS_URL` (`_ARN`, `_AUTH_TYPE`); `app/agent/gateway/client.py` turns that into a Strands `MCPClient` with SigV4 signing, which `main.py` adds to `tools` only when the URL is set (so local dev runs without it unless you export the URL). The gateway exposes the tool to the model as `process-refund___process_refund` and invokes the Lambda with the tool arguments as the event.

**Human approval** (`app/agent/gateway/approval.py`, `RefundApprovalHook`): the hook never decides which refunds need approval — that lives only in the Cedar policies. It strips any model-supplied `approved_by`, sends the call as-is, and only when the gateway denies it (`"not allowed due to policy enforcement"`) pauses the agent with a `refund_approval` interrupt. The stream then yields `{"interrupts": [{id, name, reason}]}`; the caller resumes with `{"interruptResponses": [{"interruptId": ..., "response": {"approved": true, "approver": "<name>"}}]}` (or `{"approved": false}`), and the call is retried once with `approved_by` set. `tools/chat.py` implements this loop.

**Infra** (`agentcore/cdk/`): `bin/cdk.ts` reads the project, creates one stack per entry in `agentcore/aws-targets.json` (one `default` target, region **us-west-2**; account from `$AWS_ACCOUNT_ID`, see below), and instantiates `AgentCoreStack`; it also substitutes `${AWS_ACCOUNT_ID}` in `agentcore.json` (keep that). `lib/cdk-stack.ts` is where custom infra goes: add custom AWS resources after `AgentCoreApplication` and wire them via `this.application.runtime('agent')` (`grantRead/grantWrite/grantReadWrite`, `addEnvironmentVariable`). Resources added here don't appear in `agentcore status`.

## Conventions / gotchas

- **Refund policy**: the Cedar policies live in **S3** (`s3://$CEDAR_POLICIES_BUCKET`, set in the runtime's `envVars` in `agentcore.json`; one `<name>.cedar` object per policy, named from the file with non-alphanumerics → `_`). CDK only creates the empty `RefundPolicies` engine and attaches it to the gateway (enforce mode); `policyEngines[].policies` must stay `[]`. At runtime start, `load_policies_and_run_agent()` in `main.py` calls `app/agent/policies/loader.py`, which makes the engine match the bucket exactly (create → update → delete; an empty bucket is ignored; sync errors are logged and the agent still serves). To change a guardrail, edit the S3 object — it applies when the next runtime microVM starts (i.e. a new session), not to running sessions. The engine is deny-by-default, so the gateway denies everything until the first sync. `lib/cdk-stack.ts` grants the runtime S3 read and Create/Update/Delete on this engine's policies — i.e. the agent process can rewrite its own guardrails.
- **Cedar policies are compiled against the gateway's tool manifest when they are created/updated.** If a policy references a tool input that is added later (deploy a tool schema change), the existing policy keeps the old schema and silently never matches: change or re-upload the S3 object so the next sync updates it. A policy that fails validation ends up `CREATE_FAILED`/`UPDATE_FAILED`; the sync recreates those on the next start, and logs the `statusReasons`. Compilation reads the gateway with the runtime's credentials, hence the `GetGateway`/`ListGatewayTargets`/`ManageResourceScopedPolicy` grants in `lib/cdk-stack.ts`.
- Policy validation runs with `FAIL_ON_ANY_FINDINGS`; unconditional permits are rejected as "Overly Permissive" (status `CREATE_FAILED`). `agentcore deploy` can exit 0 even when the stack rolled back — confirm with `aws cloudformation describe-stacks` / `list-policies`.

- **Account ID is kept out of git** and read from `$AWS_ACCOUNT_ID`. `agentcore/aws-targets.json` is gitignored and generated from `aws-targets.template.json` by `AWS_ACCOUNT_ID=<id> agentcore/write-aws-targets.sh` (the CLI reads that file literally, no env substitution); run it once before `agentcore deploy`. In `agentcore.json`, write the account as `${AWS_ACCOUNT_ID}` (e.g. the refund Lambda ARN); `bin/cdk.ts` substitutes it from the env var, falling back to the target's account. `tools/chat.py` builds the runtime ARN from it too. `agentcore/.cli/deployed-state.json` still contains the stack ARN (with the account) because the CLI writes it.

- Deployment region is **us-west-2**. The local AWS CLI default region is `ap-south-1`, so pass `--region us-west-2` (or set `AWS_REGION=us-west-2`) for any direct `aws` CLI calls against deployed resources, and when running `agentcore dev` against real Memory.

- `LOCAL_DEV=1` makes the app use `agentcore/.env.local` instead of AgentCore Identity. `.env.local` holds secrets — don't read or commit it.
- `agentcore/.cli/*` is gitignored except `agentcore/.cli/deployed-state.json`, which should be committed (binds a target to its stack/credential ARNs).
